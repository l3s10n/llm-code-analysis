# VulSolver

VulSolver is an LLM-based framework for repository-scale vulnerability detection through stepwise constraint solving. It distinguishes potentially dangerous source-to-sink call paths from paths whose checks, transformations, or application logic prevent exploitation.

Along each candidate path, VulSolver analyzes caller–callee hops, accounts for relevant off-path methods, and propagates a compact state of vulnerability-relevant data. The maintained state and supporting evidence are used to assess reachability and sink exploitability without repeatedly supplying the entire call chain.

The paper evaluates VulSolver on 1,023 [OWASP Benchmark](https://github.com/OWASP-Benchmark/BenchmarkJava) cases covering command injection, path traversal, and SQL injection, using six LLM backbones: GLM-4.7, Kimi-K2, DeepSeek-V3, DeepSeek-V4-Pro, GPT-4o, and GPT-4-Turbo. The table below reports **DeepSeek-V4-Pro**, the best-performing backbone overall. All rows use this same backbone, and all metrics, including F1, are percentages.

| Vulnerability Type | Accuracy | Precision | Recall | F1-Score |
| :--- | :--- | :--- | :--- | :--- |
| Overall | 99.41% | 100.00% | 98.87% | 99.43% |
| Command Injection | 99.20% | 100.00% | 98.41% | 99.20% |
| Path Traversal | 99.63% | 100.00% | 99.25% | 99.62% |
| SQL Injection | 99.40% | 100.00% | 98.90% | 99.45% |

The paper uses Kimi-K2 consistently for baseline comparisons and follow-up experiments unless otherwise specified; its overall benchmark F1 is 97.97%, with 100% recall. The best backbone can vary by vulnerability type: GLM-4.7 achieves the highest SQL injection F1 of 99.63%. These are separate configurations, not results combined into the table above.

VulSolver currently supports detection of Path Traversal, Command Injection, Code Injection, SQL Injection, and SSRF vulnerabilities. The controlled benchmark above covers command injection, path traversal, and SQL injection; it does not report benchmark scores for code injection or SSRF.

In the paper's real-world study, VulSolver analyzed ten widely used open-source projects (with star counts ranging from 1.4k to 38.2k at the time of measurement) and discovered **40+ vulnerabilities**. # Installation and Configuration

Install the required dependencies with the following command:

```bash
pip3 install -r requirements.txt
```

Then configure the model settings in `config.yaml`:

```
llm:
  base_url: "base_url_for_the_default_model"
  api_key: "api_key_for_the_default_model"
  model: "model_name_for_the_default_model"

decision_llm:
  base_url: "base_url_for_the_complex_decision_model"
  api_key: "api_key_for_the_complex_decision_model"
  model: "model_name_for_the_complex_decision_model"
```

`decision_llm` is optional and is only used for complex logic decisions. If it is left empty, VulSolver will use the `llm` configuration everywhere.

> Since VulSolver is currently built on the Claude Code SDK for agent orchestration, please ensure your `base_url` supports the Anthropic API format.

# Usage

Run the commands below from the VulSolver repository root. Results, logs, and cache files are written relative to the working directory.

For candidate paths already generated by SAST, use the [standalone path verifier](#integration-with-sast); the paths already identify their entry points, so no separate interface argument is needed. To discover paths from a named interface using the built-in `path_explore` module and then verify them, run:

```bash
python3 main.py <target_project_root_directory> <target_interface_name> # Example: python3 main.py '/tmp/helloProject' '/sample/hello'
```

To analyze multiple interfaces in one run, provide an interface list file with one interface per line. Blank lines and lines starting with `#` are ignored; interfaces are processed in file order:

```bash
python3 main.py <target_project_root_directory> --interface-file <interface_file>
```

For example:

```bash
python3 main.py '/tmp/helloProject' --interface-file './interfaces.txt'
```

If you prefer plain terminal output instead of the Textual TUI, add `--no-tui`:

```bash
python3 main.py <target_project_root_directory> <target_interface_name> --no-tui
```

You can also combine `--interface-file` and `--no-tui`:

```bash
python3 main.py <target_project_root_directory> --interface-file <interface_file> --no-tui
```

**Note:** Avoid using `sudo` or running as the root user.

During execution, VulSolver displays the analysis process in real-time via a TUI interface by default:

![VulSolver example](assets/example.jpg)

If `--no-tui` is specified, VulSolver prints progress and summary directly to the terminal.

# Viewing Results

Results are written to `results/<project_name>/<interface_name>/` relative to the working directory. For directory naming, leading and trailing `/` characters are removed from the interface name and remaining `/` characters become `_`; for example, `/example/read` becomes `example_read`.

`potential_paths.json` records candidate call chains. Each `Path` node uses a project-relative `file_path`, a `function_name`, and **1-based, inclusive** `start_line` and `end_line` values. Nodes are ordered from the entry method to the method invoking the sink; the sink expression is stored separately in `SinkExpression`. The verifier reads source code from those locations in the target checkout. The following example is also available as [a JSON file with matching Java source](examples/sast_paths/potential_paths.json):

```json
[
  {
    "InterfaceName": "/example/read",
    "Type": "PathTraversal",
    "SinkExpression": "Files.readString(Path.of(fileName))",
    "Path": [
      {
        "file_path": "ExampleController.java",
        "function_name": "read",
        "start_line": 7,
        "end_line": 9
      },
      {
        "file_path": "ExampleController.java",
        "function_name": "readFile",
        "start_line": 11,
        "end_line": 13
      }
    ]
  }
]
```

`verified_paths.json` retains `InterfaceName`, `Type`, `SinkExpression`, and the same `Path` locations, and adds the following fields:

| Field | Contents |
| :--- | :--- |
| `IsVulnerable` | Boolean exploitability verdict for this candidate path. |
| `Confidence` | Confidence label returned by the decision stage. |
| `Summary` | Explanation of the verdict. |
| `DataflowAnalysis` | Records containing `NodeIndex` (0-based), `NodeName`, `Parameters`, `MemberVariables`, and `NonLocalSources`. The last field records descriptions of non-local reads that contribute to sink semantics. |
| `FilterLogics` | Records containing `Dataflow` (the affected caller-side item), `Description`, `File`, and `Lines` (a string such as `10-20`, or `Unknown`). |

The exploration stage writes `potential_paths.json` when it finds candidate paths, and the verification stage writes `verified_paths.json` when results are produced. The standalone verifier consumes an existing candidate file rather than generating a new one.

# Viewing Logs

Logs are written to `logs/<project_name>/<interface_name>/` relative to the working directory. `path_explore.log` records interface exploration when that stage is used, while `path_verify.log` records path verification. The exploration log ends with a tree showing paths from the interface to sinks, for example:

```
<VulSolver exploration tree building process>

BenchmarkTest00011.java#doPost
    ├── Sink
    └── Sink
```

The `path_verify.log` records the detailed verification process for call chains extracted from the exploration tree. Each entry begins with the call chain header, followed by the complete verification process:

```
Type: PathTraversal
Sink Expression: new java.io.File(param, "/Test.txt")

Call Chain:
  doPost → sink

Path Nodes:
  [0] doPost
      File: BenchmarkTest00011.java

<VulSolver verification process for this call chain>
```

# Integration with SAST

VulSolver separates candidate-path construction from exploitability analysis. A SAST frontend supplies candidate source-to-sink chains from its call graph and source/sink specifications; the `path_verify` module evaluates those chains with LLM-based semantic reasoning. The frontend's exploitability verdict is not required or adopted. The built-in `path_explore` module is another way to supply candidates.

Export SAST candidates in the `potential_paths.json` format above, using source locations from the same target checkout. Group paths by `InterfaceName` into separate files: the verifier uses the first path's interface to name the run's result and log directories. Then run:

```bash
python3 -m path_verify.verify <target_project_root_directory> <path_to_potential_paths.json> --no-tui
```

After configuring a model, you can run the bundled synthetic example:

```bash
python3 -m path_verify.verify ./examples/sast_paths ./examples/sast_paths/potential_paths.json --no-tui
```

It imports the candidate path and reads the matching Java source directly, without invoking `path_explore` or requiring a running Java application. Verification still calls the configured LLM. To choose the output file, add an output path with a directory component, such as `-o ./results/example_verified.json`; omit `--no-tui` to use the Textual frontend.
